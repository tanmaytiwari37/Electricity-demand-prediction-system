# PeakWatch Delhi — Hackathon Master Plan

**Tagline:** See tomorrow's peak today.
**Problem:** PS-1, AI-based Electricity Demand Prediction System (AI + Development).
**Status:** Planning document. No implementation yet.

---

## 0. Data honesty rules (used everywhere in the product)

Every number in the app carries one of four provenance labels. The UI shows the label as a badge; the README repeats it.

| Label | Meaning | Examples in this project |
|---|---|---|
| REAL | Public data pulled from a real source | Open-Meteo historical hourly weather for Delhi, Open-Meteo 7-day forecast, Indian public holidays (Python `holidays` package) |
| SIMULATED | Generated by our own script, conditioned on real weather, calibrated to publicly reported ranges | Hourly system load, zone/feeder loads, zone capacities, rooftop-solar capacity |
| MODEL | Output of our trained model | Hourly forecasts, P10/P90 bands, peak estimates, risk levels |
| ASSUMPTION | A demo parameter we chose, editable in the UI | Grid capacity threshold (default 8,500 MW), alert thresholds (85/92/97 %), action rules |

Calibration anchors are limited to widely reported public figures: Delhi peak demand has crossed 8,000 MW in recent summers (reported around 8,600 MW in June 2024) and winter peaks are far lower. We use these only to scale the simulation. We never claim the simulated curve is Delhi's actual load, and we never claim real feeder data.

## PHASE 1 — PRODUCT STRATEGY

### 1. Interpretation
Build a DISCOM/SLDC-facing decision-support tool, not a notebook. The chain is: weather + history → hourly forecast (24 h and 7 d) → predicted peak and margin to capacity → risk alert → which zones are at risk → what to do → how much to trust it. The model is one component. The product is the workflow around it.

### 2. Personas
- **SLDC shift engineer (primary).** Balances Delhi's load in real time and prepares the day-ahead schedule. Needs tomorrow's hourly curve, the peak MW and hour, and margin to available capacity. Works in a control room, wants a glanceable screen.
- **DISCOM network-planning engineer.** Responsible for distribution zones and feeders. Needs to know which areas will run hot tomorrow afternoon so load transfers can be arranged in advance.
- **Power-procurement analyst.** Buys power a day and a week ahead. Needs the 7-day outlook and the uncertainty band to size purchases.
- **Management viewer (secondary).** Wants the headline: are we at risk tomorrow, yes or no.

### 3. Pain points
- Temperature drives demand, and a small temperature miss swings hundreds of MW. Weather and load live in separate tools.
- Peaks are the problem, not averages. Operators care about the top hour of the day and how close it is to capacity.
- Area-level overload is discovered reactively, after a trip, instead of a day early.
- Forecasts arrive as spreadsheets without uncertainty, so nobody knows how much to trust them.
- No quick way to ask "what if it is hotter than forecast".

### 4. What an operator needs from the system
- Hourly forecast for the next 24 h and 7 d with an uncertainty band.
- Peak MW, peak hour, hours until peak, and margin to capacity.
- A traffic-light risk level with a plain-language reason.
- Zone breakdown with utilisation percentage and overload flags.
- A what-if temperature control that answers in under a second.
- A track record: how accurate the model has been versus a naive rule.
- A tool that keeps working when the internet or a data feed drops.

### 5. Essential features (must ship)
1. Data pipeline: real weather download plus simulated load generator, both cached locally.
2. Forecast model with two naive baselines and a linear baseline, evaluated on a held-out summer.
3. FastAPI backend serving history, forecast, alerts, zones, what-if, and metrics.
4. React dashboard: KPI row, forecast chart with capacity line and uncertainty band, alert feed, zone grid.
5. What-if temperature simulation.
6. Offline demo mode from a bundled snapshot.

### 6. Optional features (build if on schedule)
- Rooftop-solar net-demand slider.
- Forecast driver explanation ("why is tomorrow high").
- Rule-based recommended actions per zone.
- 7-day view tab and temperature-vs-demand scatter.
- Deployment to Render and Vercel.

### 7. Do not build
- Login, roles, user management.
- PostgreSQL or any database. Files are enough.
- WebSockets or live streaming.
- LSTM or transformer models.
- A scraper for the Delhi SLDC website.
- Email/SMS notifications, a chatbot, a mobile app, multi-city support, a scheduler.

### 8. What makes this stand out
- An honest model scorecard with a skill score against naive baselines, on screen, not buried in a notebook.
- Quantile prediction intervals, so uncertainty is visible in the chart.
- Instant what-if temperature simulation that re-runs the real model.
- Zone-level overload risk with concrete rule-based actions.
- Provenance badges on every panel. Judges trust a team that labels its own simulation.
- Works fully offline from a snapshot. Nothing in the demo depends on Wi-Fi.
- Framed around the real day-ahead scheduling workflow rather than a generic dashboard.

### 9. Name and tagline
**PeakWatch Delhi** — "See tomorrow's peak today."
Alternatives if taken: GridSense Delhi, LoadLens.

### 10. Demo storyline (short version, full script in Phase 13)
Problem in 20 seconds → today's live view → tomorrow's forecast and peak → red alert with margin → zones at risk → what-if +2 °C → recommended actions → model scorecard versus baseline → why it matters and what is real versus simulated.

## PHASE 3 — ML STRATEGY

### Model comparison

| Approach | Strengths | Weaknesses for this task | Verdict |
|---|---|---|---|
| Prophet | Easy trend and seasonality, built-in intervals | Weak with hourly double seasonality plus non-linear temperature response; cmdstan install is painful on Windows and Python 3.13; slow to refit for what-if | Skip |
| ARIMA / SARIMA / SARIMAX | Classic, statistically principled | Hourly data with 24 h and 168 h seasonality needs Fourier terms and is slow on ~40k rows; linear in temperature; awkward what-if | Skip (mention in docs as considered) |
| Random Forest | Robust, non-linear | Slower, large model files, no native quantile loss, cannot extrapolate above seen loads | Skip |
| Gradient boosting (scikit-learn `HistGradientBoostingRegressor`) | Fast to train (seconds), handles non-linear temperature, native quantile loss for intervals, handles NaN, no extra dependency, sub-second inference for what-if | Needs careful lag design to avoid leakage; extrapolation above historical max is limited | **Choose** |
| Ridge regression with the same features | Simple, interpretable | Underfits the temperature curve | Use as linear baseline |
| Hybrid (Prophet residuals + GBM) | Slightly better in papers | Doubles complexity for marginal gain | Skip |

### Design
- **Two direct models by horizon**, each trained as three quantile regressors (P10, P50, P90):
  - Day-ahead model: predicts hours 1–24 ahead. Allowed lags: 24 h, 48 h, 168 h, 336 h, plus previous-day peak and mean.
  - Week-ahead model: predicts hours 25–168 ahead. Allowed lags: 168 h, 336 h, 504 h only.
  - Rule: every lag or rolling window is shifted by at least the horizon it serves. This is the leakage guard.
- **Target:** `load_mw` at each hour.
- **Preprocessing:** hourly index in IST, reindex to a complete range, linear interpolation for gaps up to 3 hours, drop longer gaps from training, clip impossible values, join weather by hour.
- **Features:**
  - Calendar: hour, day of week, weekend flag, month, holiday flag, sin/cos of hour and day-of-year, season.
  - Weather: temperature, apparent temperature, humidity, wind speed, cloud cover, shortwave radiation. Derived: cooling degree hours `max(temp − 24, 0)`, heating degree hours `max(15 − temp, 0)`, daily max and mean temperature, 3-day rolling mean temperature (heat build-up).
  - Load history: the horizon-safe lags above, same-hour mean and max over the previous 7 days (shifted), previous-day peak.
  - Training uses actual historical weather; inference uses Open-Meteo forecast weather. We acknowledge this mismatch and, as an optional step, add small Gaussian noise to training temperatures so the model is not over-confident in perfect weather.
- **Solar** is not a model feature. It is a post-hoc adjustment: `net = gross − solar_mw`, where solar is computed from real shortwave radiation and a user-set installed capacity.
- **Split (time-ordered, no shuffling):**
  - Train: 2022-01-01 to 2025-08-31
  - Validation: 2025-09-01 to 2026-03-31 (hyperparameters, early stopping)
  - Test: 2026-04-01 to 2026-08-31 (a full summer, reported once, never tuned on)
- **Metrics:** MAE, RMSE, MAPE, daily-peak MAE, peak-hour hit rate within ±1 h, P10–P90 coverage (target near 80 %).
- **Baselines:** Naive-24 (same hour yesterday), Naive-168 (same hour last week), Seasonal profile (mean of last 4 weeks same weekday and hour), Ridge regression on the same features.
- **Skill score** shown in the UI: `1 − MAE_model / MAE_naive168`.

### How we prove the model beats the baseline
The Model tab shows a scorecard table and a bar chart of MAE for every baseline and the model on the same test summer, plus a backtest replay chart of predicted versus actual for the hottest test week. The README reproduces the table. All figures are labelled as measured on simulated load with real weather, not on Delhi's actual grid.

Expected outcome on the simulated data: the model should roughly halve the MAE of Naive-168. We report whatever the script measures and do not round up.

## PHASE 4 — DATA STRATEGY

### Reality check on public sources
- **Open-Meteo:** hourly historical archive from 1940 and a 16-day forecast, no key. Fully usable. REAL.
- **data.gov.in:** mostly monthly or annual energy statistics at state level. Not hourly load. Not usable for training in 10 hours.
- **Grid-India / POSOCO daily reports:** PDFs with daily peak per state. Useful only as calibration anchors.
- **Delhi SLDC website:** shows real-time and some historical load, but scraping and aligning it is a multi-hour risk with no guarantee.

**Decision:** real weather plus a simulated hourly load series calibrated to public ranges, with a drop-in adapter so a real CSV (`timestamp, load_mw`) can replace the simulation later without code changes.

### Load simulation design (SIMULATED, documented in `docs/DATA.md`)
For each hour `t` with real temperature `T`:
```
base(hour, weekday)          # normalised daily shape: winter evening peak ~19:00; summer afternoon ~15:00 and late-night ~23:00
season(dayofyear)            # smooth annual cycle
temp_response(T)             # 0 below 24 °C, rising steeply above; mild rise below 15 °C for winter heating
heat_buildup(T_3day_mean)    # consecutive hot days push demand higher
growth(year)                 # ~4 % per year trend
holiday_factor               # −8 % on public holidays, −5 % on Sundays
noise                        # AR(1) noise so errors are correlated like real load
load = scale × base × season × (1 + temp_response + heat_buildup) × growth × holiday × (1 + noise)
```
`scale` is chosen so the simulated June 2024 peak lands in the 8,400–8,700 MW range and the winter peak near 5,500 MW. The generator is seeded, so every run is reproducible.

### Zones (SIMULATED)
Twelve demo zones named after Delhi districts with a profile type each. Names are geographic labels only; no real feeder data is implied.

| Zone | Profile | Share of system | Behaviour |
|---|---|---|---|
| South Delhi | residential | 11 % | strong evening and night AC peak |
| Central (CP) | commercial | 7 % | daytime peak, low weekend |
| North West | mixed | 12 % | average shape |
| West | residential | 10 % | evening peak |
| East | residential | 9 % | evening peak |
| North East | dense residential | 8 % | sharp night peak |
| North | mixed | 7 % | average |
| Bawana | industrial | 8 % | flat, weekday heavy |
| Okhla | industrial-commercial | 7 % | daytime, weekday heavy |
| Dwarka | residential | 8 % | evening peak, high growth |
| Rohini | residential | 7 % | evening peak |
| New Delhi (NDMC) | institutional | 6 % | daytime peak |

Zone load = system load × share × profile modifier(hour, weekday) × (1 + zone noise), renormalised so zones sum to the system. Each zone has a simulated capacity set so that two or three zones exceed 95 % on the hottest simulated days. This guarantees a compelling but honest demo.

### Solar (SIMULATED capacity, REAL irradiance)
`solar_mw = installed_mw × (shortwave_radiation / 1000) × 0.75`. Default installed capacity 500 MW as an assumption; slider from 0 to 2,000 MW.

## PHASE 5 — SYSTEM ARCHITECTURE

```
React + Vite + Tailwind + Recharts  (frontend/)
        │  fetch /api/*  (VITE_API_URL, defaults to http://localhost:8000)
        ▼
FastAPI  (backend/app)
   ├── loads models/*.joblib once at startup
   ├── loads data/processed + data/simulated + weather cache
   ├── ForecastService: builds features for the horizon, runs P10/P50/P90
   ├── AlertService: compares forecast to capacity, computes risk levels
   ├── ZoneService: splits system forecast into zones, flags overload
   ├── WhatIfService: shifts temperature features, reruns model
   └── SnapshotService: bundles everything into one JSON
        │
        ▼
ML  (ml/)  offline scripts: generate data → build features → train → evaluate → export snapshot
        │
        ▼
Data (data/)  CSV, parquet, JSON files. No database.
```

### API endpoints
| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | liveness |
| GET | `/api/status` | data freshness, weather source (live or cache), model version, provenance flags |
| GET | `/api/history?hours=48` | recent actual load and temperature |
| GET | `/api/forecast?horizon=24|168` | hourly P10/P50/P90, peak summary |
| GET | `/api/zones/forecast?horizon=24` | per-zone hourly forecast, utilisation, risk |
| GET | `/api/alerts` | current alert list with level, reason, window |
| POST | `/api/whatif` | body `{temp_delta_c, solar_mw}` → adjusted forecast, peak, alerts |
| GET | `/api/model/metrics` | test-set scorecard for model and baselines |
| GET | `/api/model/importance` | permutation feature importance |
| GET | `/api/weather/forecast` | Open-Meteo forecast used, with source flag |
| GET | `/api/snapshot` | full bundle for the UI in one call |

### How the flow works end to end
1. `ml/` scripts run once before the demo. They download weather, simulate load and zones, build features, train and evaluate models, and write `models/` and `data/snapshot/demo_snapshot.json`.
2. FastAPI starts, loads the models and data into memory, tries to refresh the Open-Meteo forecast, and falls back to the cached forecast if the network fails. `/api/status` reports which one is in use.
3. The React app calls `/api/snapshot` on load. If the backend is unreachable it imports the bundled `demo_snapshot.json` and shows a DEMO MODE badge. Every panel renders from the same snapshot shape either way.
4. What-if calls `/api/whatif` live. In offline mode the UI reads a precomputed grid of scenarios inside the snapshot (temperature −4 to +6 °C in 1 °C steps, solar 0 to 2,000 MW in 500 MW steps).

### Database
None. The demo has one user, no writes, and data that fits in memory. A database adds setup time and a failure point without adding a feature.

### Deployment (optional, after the local demo works)
- Backend: Render free web service from `docker/Dockerfile.backend`. It sleeps after inactivity, so open it 5 minutes before judging.
- Frontend: Vercel from `frontend/` with `VITE_API_URL` set to the Render URL.
- Single-container alternative: FastAPI serves the built frontend from `/`. One Docker image, deployable to Hugging Face Spaces or Render.
The local laptop demo remains the primary path. Deployment is a bonus, never a dependency.

## PHASE 7 — UNIQUE HACKATHON FEATURES

1. **Peak-risk early warning.** Risk level from margin to capacity: Normal below 85 %, Watch 85–92 %, Warning 92–97 %, Critical above 97 %. Shows hours until peak and the risk window. Uses the P90 band, so a "Warning" means even the optimistic case is tight.
2. **What-if temperature simulation.** Slider from −4 to +6 °C reruns the actual model on shifted weather features. The peak delta updates in real time. Directly answers "what if tomorrow is 2 °C hotter".
3. **Zone overload risk with recommended actions.** Utilisation per zone per hour, and rule-based actions such as "Pre-arrange load transfer from South Delhi to North West between 14:00 and 17:00" or "Issue demand-response notice to commercial consumers in Central". Labelled as rule-based decision support, not an optimiser.
4. **Explainable forecast drivers.** A one-line explanation built from counterfactuals: run the model with last week's temperature and compare. Output: "Tomorrow's peak is +540 MW versus last week; about 480 MW is explained by the +3 °C forecast, the rest by the weekday effect." Plus permutation feature importance.
5. **Rooftop-solar net-demand slider.** Real irradiance forecast times a user-set installed capacity, shown as gross versus net curves. Demonstrates the optional requirement with honest labelling.

Skipped on purpose: anomaly detection (adds a model and a story without changing the demo), automatic load-balancing optimisation (too easy to challenge).

## PHASE 14 — JUDGING STRATEGY

### Technical points to emphasise
- Direct multi-horizon quantile gradient boosting with leakage guards enforced by tests.
- Real weather integration with automatic cache fallback and a visible source flag.
- Clean separation: offline ML pipeline, stateless API, snapshot-driven UI.
- Offline demo mode and precomputed what-if grid as deliberate reliability engineering.

### AI/ML points to explain
- Why gradient boosting beat Prophet and SARIMA for hourly demand with non-linear temperature response.
- Why lags are horizon-safe and what leakage would have looked like.
- What P10/P90 mean and how coverage is measured.
- Skill score against naive baselines rather than raw accuracy.

### Likely questions and strong answers
- **"Is this real Delhi load data?"** No. Weather is real from Open-Meteo. Load is simulated, conditioned on real temperature, calibrated to publicly reported peak ranges, and labelled everywhere. The adapter accepts a real CSV without code changes.
- **"How accurate is it really?"** We report test-summer metrics on the simulated series versus naive baselines. We make no claim about accuracy on the actual grid until real data is loaded.
- **"Why not deep learning?"** Hourly demand with a strong temperature signal is well handled by boosted trees, which train in seconds, give quantiles natively, and allow instant what-if. An LSTM would add training time and remove explainability without a clear gain at this data size.
- **"Where does the 8,500 MW capacity come from?"** It is a demo assumption, editable in the UI. Real available capacity varies daily with scheduled generation and imports, which an SLDC would supply.
- **"How would this be deployed for a DISCOM?"** Nightly retraining script, a real load feed replacing the simulator, and the same API. The architecture already separates those pieces.
- **"What about feeder-level data?"** Zones are simulated with distinct profiles to demonstrate the workflow. Real feeder data would drop into the same schema.
- **"How do you handle weather forecast error?"** The intervals partly absorb it, and the what-if slider lets operators explore it explicitly. Training with temperature noise is an option we expose.

### Limitations to acknowledge openly
Simulated load and zones, an assumed capacity, no real-time feed, no optimisation of load transfers, model trained on actual weather but scored with forecast weather in operation.

### Showing this is more than a dashboard
The what-if reruns the model live, alerts derive from quantiles, tests prove the absence of leakage, and the scorecard compares against baselines. A dashboard shows numbers; this one shows numbers with uncertainty, provenance, and a decision.
